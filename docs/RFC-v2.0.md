# Windows 现代本地音乐播放器

## 完整技术方案与开发规范 · RFC v2.0

**目标平台：** Windows 10 / Windows 11  
**项目类型：** 本地桌面音乐播放器  
**主要用途：** 个人长期使用  
**核心技术：** Rust + Tauri v2 + Svelte 5  
**开发方式：** Codex / Claude Code 辅助开发  
**方案状态：** 正式技术基线

---

# 1. 项目愿景

## 1.1 产品定位

打造一款现代、强大、易用的 Windows 本地音乐播放器，兼顾：

- **foobar2000 的可靠播放能力**
    
- **MusicBee 的丰富曲库管理**
    
- **Apple Music / Spotify 的现代交互体验**
    

不以全面复刻这些软件为目标，而是吸收其中适合个人本地音乐管理的功能与设计。

播放器应具有以下特点：

1. 音乐播放稳定、音质可靠。
    
2. 能够高效管理大型本地音乐库。
    
3. 界面美观、简洁、操作流畅。
    
4. 支持歌词、封面、歌单等丰富功能。
    
5. 支持 Windows 系统集成。
    
6. 在普通电脑上保持合理的 CPU、GPU 与内存占用。
    
7. 方便持续增加功能和改进界面。
    
8. 默认离线运行，不依赖服务器或账号。
    

## 1.2 开发原则

### 稳定性优先

播放音乐是软件最重要的功能。界面动画、数据库扫描、文件操作都不能干扰正常播放。

### 体验优先

优先考虑日常使用的便利性，而不是技术参数的极限表现。

### 本地优先

用户的音乐、歌单、数据库和设置都保存在本地。

### 适度模块化

确保主要模块职责清晰，但不强制建立复杂的分层框架或大量 Trait。

### 渐进式增强

先构建完整、稳定、好用的播放器，再增加高级音频处理与复杂视觉效果。

### AI 开发友好

项目结构和接口应易于理解、测试、修改，并通过文档约束 AI Agent 的修改范围。

## 2.1 选型说明

采用 Tauri + Svelte，而不是纯 Rust UI，主要是因为：

- 更容易制作现代、精致的播放器界面。
    
- 组件化开发自然，适合歌词、曲库和播放控制等界面。
    
- Svelte 5 响应式能力足够优秀。
    
- UI 可以与 Rust 音频引擎独立开发。
    
- AI 能比较方便地修改样式、布局和交互。
    
- 复杂动画可以按需使用浏览器渲染能力。
    

接受的技术成本包括 WebView2 运行开销、IPC 设计和跨语言调试。

对于个人长期使用，这些成本是合理的。

## 2.2 依赖管理

- 优先选择稳定、活跃维护的依赖。
    
- 兼容性优先于追逐最新版本。
    
- 提交 Cargo.lock 和 pnpm-lock.yaml。
    
- 涉及 RC 版本的 tauri-specta / Specta 必须固定兼容版本。
    
- 新依赖必须有明确用途。
    
- 定期升级，但避免一次性升级整个技术栈。

# 3. 系统整体架构

## 3.1 架构模式

采用轻量模块化分层架构。

主要分为四层。

### 第一层：Svelte UI

负责：

- 界面展示。
    
- 用户交互。
    
- 视觉动画。
    
- 页面导航。
    
- 临时 UI 状态。
    
- 歌曲列表与歌词渲染。
    

### 第二层：Tauri 通信层

负责：

- 命令调用。
    
- 数据类型转换。
    
- 事件通知。
    
- 扫描进度传输。
    
- Rust 与 TypeScript 的类型契约。
    

### 第三层：Rust 应用服务层

负责：

- 播放器状态。
    
- 播放队列。
    
- 曲库管理。
    
- 歌单管理。
    
- 歌词加载。
    
- 设置与任务调度。
    

### 第四层：基础设施

负责：

- 音频解码。
    
- 音频输出。
    
- 数据库。
    
- 文件系统。
    
- 音乐元数据。
    
- Windows 系统 API。
    

## 3.2 基本规则

1. 音频引擎不能依赖 Svelte、WebView 或具体 UI 组件。
    
2. Svelte 不能直接访问音频设备。
    
3. Rust 是真实播放状态的唯一权威来源。
    
4. 数据库与文件扫描不能阻塞音频输出。
    
5. 所有跨端通信使用明确的数据类型。
    
6. 前端业务组件通过统一的 Service 层调用 Rust。
    
7. 具体基础设施实现尽量隐藏在应用服务后面。
    

不要求每一层都通过复杂 Trait 或抽象工厂连接。

# 5. Svelte 5 前端架构

这是相对于 SolidJS 版本最重要的调整。

## 5.1 统一使用 Runes

新代码使用 Svelte 5 的响应式模型：

- `$state`：可变响应式状态。
    
- `$derived`：派生状态。
    
- `$effect`：必要的副作用。
    
- `$props`：组件参数。
    
- `$bindable`：确实需要双向绑定时使用。
    

不在新组件中使用旧版的 `$:` 响应语法或 `on:click` 写法。

避免将 `$effect` 当作通用状态更新工具。

能够使用 `$derived` 表达的派生关系，不通过 `$effect` 手动同步。

## 5.2 状态分层

前端状态分为三类。

### 组件本地状态

例如：

- 菜单是否打开。
    
- 弹窗状态。
    
- 当前悬停项目。
    
- 输入框内容。
    
- 临时拖拽状态。
    

使用组件内 `$state`。

### 共享 UI 状态

例如：

- 当前主题。
    
- 当前页面。
    
- 侧边栏是否展开。
    
- 播放队列面板状态。
    
- 歌词展示模式。
    
- 曲库筛选条件。
    

使用独立的 `.svelte.ts` 文件管理。

### 后端业务状态

例如：

- 当前播放曲目。
    
- 实际播放状态。
    
- 当前播放队列。
    
- 音频输出设备。
    
- 曲库歌曲数据。
    

由 Rust 维护，前端保存只读状态快照或用于展示的响应式副本。

## 5.3 前端状态示例

可以设计：

```
stores/
├── player.svelte.ts
├── navigation.svelte.ts
├── theme.svelte.ts
├── library.svelte.ts
└── lyrics.svelte.ts
```

其中 `player.svelte.ts` 负责：

- 保存当前 PlayerSnapshot。
    
- 处理后端推送的播放状态。
    
- 提供 UI 可以读取的响应式字段。
    
- 调用统一的播放器 Service。
    

但不直接解码音频，也不自行维护第二套真实播放队列。

## 5.4 数据与展示分离

推荐数据流：

```
Svelte Component
       ↓
Frontend Service
       ↓
Tauri Command
       ↓
Rust Player Controller
       ↓
Audio Engine / Database
       ↓
State Snapshot / Result
       ↓
Svelte Reactive State
       ↓
UI Update
```

Svelte 组件尽量只处理展示和操作。

复杂数据处理放进独立的 TypeScript 工具或 Rust 服务中。

## 5.5 页面组织

不默认引入 SvelteKit。

使用 Vite 构建单页桌面应用。

初期采用简单的页面状态和组件切换。

页面数量增加、确实需要深层导航和历史记录后，再考虑引入专门的路由方案。

## 5.6 组件规范

建议：

- 每个组件具有清晰职责。
    
- 通用组件不包含具体业务逻辑。
    
- 页面组件负责组合功能组件。
    
- 不把整个播放器写在一个 App.svelte 中。
    
- 公共颜色、尺寸与动画时长通过 Design Tokens 管理。
    
- 不强制每个文件少于固定行数。
    
- 尽量避免过多组件之间的双向状态依赖。
    

## 5.7 Svelte 生命周期管理

- 通过 `onMount` 建立需要浏览器环境的监听。
    
- 组件销毁时释放事件订阅和观察器。
    
- 播放页面切换不能导致重复订阅。
    
- 长时间运行的动画需要支持暂停和销毁。
    
- 后台隐藏时降低不必要的渲染频率。

- 深色主题优先。

- 以专辑封面作为视觉焦点。
    
- 少量强调色。

- 字体：系统中文字体与 Segoe UI 等系统字体合理回退。

## 6.5 主题系统

# 7. 音频播放引擎

## 7.1 播放架构

核心链路：

```
Audio File
    ↓
Symphonia Demux / Decode
    ↓
PCM Samples
    ↓
Buffer
    ↓
Format Conversion
    ↓
Optional Resampler / DSP
    ↓
cpal Output Stream
    ↓
Windows Audio Device
```

音频引擎由 Rust 实现。

前端不使用 HTML Audio 元素承担主要音乐播放工作。

## 7.2 音频格式

第一阶段目标：

- MP3
    
- FLAC
    
- WAV
    
- OGG Vorbis
    
- AAC / M4A
    
- ALAC
    
- AIFF（按需）
    

实际支持需要验证解码器的对应 feature、容器和编码变体。

不以“支持所有格式”作为初期目标。

后续可评估 Opus、WavPack 等格式的扩展解码实现。

## 7.3 音频输出

初期使用 cpal。

默认：

- Windows 默认输出设备。
    
- 共享模式。
    
- 合理缓冲大小。
    
- 自动匹配或转换采样率。
    
- 支持基础音量控制。
    

后续扩展：

- 输出设备选择。
    
- 默认设备变化检测。
    
- WASAPI 独占模式。
    
- 更详细的采样格式和缓冲设置。
    

## 7.4 线程模型

至少区分：

**解码工作线程**

负责文件读取、解码、Seek 和 PCM 数据准备。

**音频输出线程 / 回调**

负责从准备好的缓冲区取数据并提交给音频设备。

**应用服务任务**

负责播放队列、状态控制、曲库访问。

**UI 渲染线程**

由 WebView2 / Svelte 负责。

音频回调中不执行数据库查询、文件读取、阻塞等待或复杂日志操作。

采用有界 PCM 缓冲区，必要时使用成熟的 SPSC 环形缓冲库。

## 7.5 播放状态

建议状态：

- Idle
    
- Loading
    
- Playing
    
- Paused
    
- Stopped
    
- Error
    

需要时增加 Buffering、Recovering。

Rust 维护真实状态。

在播放设备成功启动之前，不向前端报告已成功播放。

## 7.6 播放队列

支持：

- 添加歌曲。
    
- 添加整个专辑。
    
- 添加歌单。
    
- 立即播放。
    
- 添加到下一首。
    
- 添加到队列末尾。
    
- 删除队列项目。
    
- 手动排序。
    
- 清空队列。
    
- 顺序、随机、单曲循环、列表循环。
    

随机播放应保留必要的播放历史，避免“上一曲”功能行为混乱。

## 7.7 Seek 与切歌

Seek 需要：

1. 接受指定目标时间。
    
2. 使旧解码和缓冲数据失效。
    
3. 解码器移动到目标位置。
    
4. 重新填充缓冲区。
    
5. 更新播放器状态。
    
6. 向 UI 发送实际结果。
    

使用曲目版本或请求序号避免旧操作结果覆盖新状态。

## 7.8 播放进度

播放器内部记录实际播放位置。

前端根据状态快照和单调时钟平滑插值。

不需要每帧从 Rust 请求播放进度。

播放暂停、Seek、切歌后立即校正前端位置。

在窗口隐藏时降低或暂停视觉插值更新。

## 7.9 后期音频增强

根据使用需求增加：

- Gapless。
    
- ReplayGain。
    
- Rubato 重采样。
    
- 均衡器。
    
- Crossfade。
    
- WASAPI 独占模式。
    
- 音频可视化。
    

无缝播放必须处理编码延迟、尾部填充和采样边界，不能只靠提前缓冲。

Bit-perfect 如果未来要实现，应作为独立的高级播放模式考虑，并明确与 EQ、软件音量和重采样的冲突。

- 搜索。

## 8.7 增量扫描

处理：

- 新增文件。
    
- 删除文件。
    
- 文件重命名。
    
- 文件内容变化。
    
- 文件夹移动。
    

监听事件需要去抖动与合并。

应用启动时进行必要的轻量校验，防止休眠或退出期间的文件变化被遗漏。

文件暂时找不到时先标记为不可用，尽量保留歌单关联。

├── duration_ms

## 11.4 错误处理

Rust 命令返回统一、可序列化的错误类型。

例如：

- 文件不存在。
    
- 不支持该格式。
    
- 设备无法打开。
    
- 文件正在被占用。
    
- 数据库暂时不可用。
    

避免直接把底层调试字符串原样显示给用户。

## 11.5 自动类型绑定

使用 tauri-specta 生成前端接口。

生成文件禁止手动编辑。

如果该依赖在当前版本组合中存在问题，可以先使用手工定义的集中式类型与 API 封装，等版本稳定后再接入自动生成。

# 14. 性能优化方案

## 14.1 主要原则

性能优化以实际体验为准。

避免过早针对某个框架的理论性能进行复杂设计。

## 14.2 UI 性能

- 使用 Svelte 5 细粒度响应式更新。
    
- 大型歌曲列表虚拟化。
    
- 避免不必要的全局状态更新。
    
- 滚动期间避免加载完整大封面。
    
- 使用图片尺寸缓存。
    
- 减少大面积 CSS Blur。
    
- 尽量使用 transform 和 opacity 动画。
    
- 动态背景支持关闭。
    
- 后台窗口降低视觉计算。
    

## 14.3 音频性能

- 解码与音频输出分离。
    
- 使用有界 PCM 缓冲。
    
- 避免音频回调中的锁等待与分配。
    
- 对可能产生断音的情况记录统计。
    
- 按实际设备情况调整缓冲策略。
    

## 14.4 数据库性能

- 建立必要索引。
    
- 使用批量事务。
    
- 搜索索引。
    
- 异步分页查询。
    
- 文件变化增量更新。
    
- 避免无意义的全曲库重新扫描。
    

## 14.5 初步性能目标

这些是优化方向，不是未经测试的保证。

|项目|初步目标|
|---|---|
|启动速度|常用 SSD 电脑上约 2 秒内可交互|
|常规操作|操作反馈无明显迟滞|
|曲库搜索|常见查询体感即时|
|曲库规模|优先保障数万首，逐步测试十万首|
|列表滚动|60 FPS 为基本目标|
|高刷体验|硬件允许时进一步优化|
|长时间播放|不出现软件导致的异常中断|
|内存使用|稳定、可控、不持续增长|
|后台使用|不产生无意义的高 CPU/GPU 占用|

测试时记录机器配置、测试数据规模和冷 / 热缓存状态。

# 15. 稳定性与异常处理

必须覆盖以下问题：

1. 音乐文件损坏或格式不支持。
    
2. 音乐文件被移动、删除。
    
3. 输出设备突然断开。
    
4. Windows 默认输出设备切换。
    
5. 系统休眠及唤醒。
    
6. 解码器异常。
    
7. 数据库损坏或迁移失败。
    
8. 曲库扫描途中取消。
    
9. 大量文件扫描导致资源压力。
    
10. 软件异常退出。
    

处理原则：

- 不崩溃优先。
    
- 能恢复则自动恢复。
    
- 无法恢复时明确提示。
    
- 不丢失歌单和设置。
    
- 不擅自删除或修改原始音乐。
    
- 关键错误记录到日志。
    

使用 tracing 进行日志管理。

日志容量需要限制，不允许无限增长。

# 16. 数据安全与本地隐私

## 16.1 文件安全

- 默认只读取用户音乐文件。
    
- 标签编辑需要用户明确操作。
    
- 删除曲库记录不等于删除磁盘文件。

数据库、日志、设置和封面缓存放在 Windows 标准应用数据目录。

分离用户数据与可重建缓存。

## 16.3 Tauri 安全

- 使用最小必要的 Capabilities。
    
- 不随意暴露文件系统能力。
    
- 不加载不受信任的远程页面。
    
- 自定义资源协议限制访问范围。
    
- Rust 命令验证输入参数。

# 18. AI Agent 开发规范

## 18.1 核心要求

Codex / Claude Code 进行开发时应：

1. 先阅读 AGENTS.md。
    
2. 理解相关模块的现有逻辑。
    
3. 不随意替换技术框架。
    
4. 优先修改现有模块。
    
5. 不创建没有必要的抽象层。
    
6. 不擅自调整数据库结构。
    
7. 不随意修改音频实时线程。
    
8. 不使用 Mock 假装功能已经实现。
    
9. 新增功能时补充必要测试。
    
10. 完成任务后运行对应检查。
    

## 18.2 Svelte 专项规则

- 新组件统一使用 Svelte 5 Runes。
    
- 不混用旧版 Svelte 状态语法。
    
- 共享状态放到明确的 `.svelte.ts` 模块。
    
- 不在视图组件内直接散落 Tauri invoke 调用。
    
- 后端接口统一通过 Services 层。
    
- 事件订阅必须正确释放。
    
- 不通过 `$effect` 构造复杂、循环的状态同步。
    
- 派生状态优先使用 `$derived`。
    
- 大型列表必须考虑虚拟化。
    
- 禁止无理由增加全局状态。
    

## 18.3 Rust 专项规则

- 不在音频实时回调中进行阻塞 IO。
    
- 不在音频回调中进行数据库访问。
    
- 不允许 UI 状态反向控制底层实现细节。
    
- 数据库变更必须提供迁移。
    
- 不能忽略重要错误。
    
- 不使用 `.unwrap()` 掩盖正常运行时可能发生的失败。
    
- 优先复用可靠的成熟 crate。
    
- 避免无意义的 Trait 和多层抽象。
    

## 18.4 分任务开发

每个任务应说明：

# 22. 最终架构决策

## 正式采用

**Rust + Tauri v2 + Svelte 5 + TypeScript + Vite + Tailwind CSS**

Rust 负责：

- 音频。
    
- 曲库。
    
- 歌单。
    
- 元数据。
    
- 数据库。
    
- Windows 集成。
    

Svelte 5 负责：

- 界面。
    
- 动画。
    
- 页面。
    
- 视觉状态。
    
- 歌词展示。
    
- 用户交互。
    

Tauri 负责：

- 桌面窗口。
    
- 前后端通信。
    
- 系统能力接入。
    
- 应用打包。
    

## 最终原则

**播放必须可靠。**

**界面必须舒服。**

**功能必须实用。**

**性能必须合理。**

**架构必须容易理解和维护。**

**开发复杂度必须与实际需求匹配。**

第一阶段到第三阶段完成后，项目就应该成为一款真正能长期使用的本地音乐播放器。

之后的专业音频和高级视觉功能，以实际使用体验决定是否开发，而不是为了追求规格而增加复杂度。
